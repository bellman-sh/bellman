# ADR 0033 — A2A: a public room answers outside agents

**Date:** 2026-10-23 · **Status:** Accepted · **Spec:** `docs/superpowers/specs/2026-10-23-a2a-design.md` · **Plan:** `docs/superpowers/plans/2026-10-23-a2a.md`

## Context

Agents built on Google ADK, CrewAI, Strands and Microsoft Agent Framework call remote agents over A2A and never speak MCP, so none of them can reach a public room. The design (spec D1 to D9) has `mcp.bellman.sh/a2a` answer them, one card per public room.

The design left three facts to the builder (D5, D8 and "What's left to the builder"), and each one decides a later task: which A2A versions the endpoint accepts, whether the JSON-RPC layer can use `@a2a-js/sdk` on Workers, and how long the Worker may hold a blocking `SendMessage`. The Verified section records what was checked, and the Rulings section records what it decided. Decision and Consequences follow.

## Verified

Checked on 2026-10-23, from package source and registry metadata, not from blog posts. Package contents were read from the published wheels and tarballs; the links point to the same code on GitHub or the registry.

### 1. Which A2A version each client sends

The Python A2A clients all sit on `a2a-sdk` (Python), so the version they send is the version of `a2a-sdk` they pin.

- **`a2a-sdk` 0.3.x** ([0.3.26](https://pypi.org/project/a2a-sdk/0.3.26/)) sends **no `A2A-Version` header** (the string does not appear in the package) and calls `message/send`, `message/stream`, `tasks/get`, `tasks/cancel`, `tasks/resubscribe` ([`client/transports/jsonrpc.py`](https://github.com/a2aproject/a2a-python/blob/v0.3.26/src/a2a/client/transports/jsonrpc.py)). It posts to the card's top-level `url`. Its types have no `tenant` field.
- **`a2a-sdk` 1.x** ([1.2.3](https://pypi.org/project/a2a-sdk/1.2.3/)) sends **`A2A-Version: 1.0`** on every request (`ClientFactory` sets it on the HTTP client, [`client/client_factory.py`](https://github.com/a2aproject/a2a-python/blob/v1.2.3/src/a2a/client/client_factory.py)) and calls `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`, `SubscribeToTask` ([`client/transports/jsonrpc.py`](https://github.com/a2aproject/a2a-python/blob/v1.2.3/src/a2a/client/transports/jsonrpc.py)). It falls back to a 0.3 transport only when the card's interface says `protocolVersion` 0.3; that transport sends `A2A-Version: 0.3` and the 0.3 method names.

What this means for the endpoint:

- **CrewAI and Strands are 0.3-only clients**, and between them they are half of the four named in the design. They send no `A2A-Version` header, which the spec reads as 0.3. They call the 0.3 method names and read a 0.3 card, in which `url`, `name`, `description`, `version`, `capabilities`, `defaultInputModes`, `defaultOutputModes` and `skills` are all required (`AgentCard` in `a2a-sdk` 0.3.26 `types.py`).
- **0.3 has no `tenant`.** The 0.3 client posts to the card's `url`, so a 0.3 caller can name a room only through that URL. A 0.3 card for a room has to carry the room in its `url` (for example `https://mcp.bellman.sh/a2a/<room>`); the `tenant` field in the request body cannot do it.
- ADK and Microsoft Agent Framework send 1.0 and need nothing beyond the design as written. ADK will send 0.3 if a user pins `a2a-sdk` below 1.0, and then it needs the same 0.3 path.
- If a 0.3 client talks to a card whose interface says 0.3, `a2a-sdk` 1.x sends `A2A-Version: 0.3` (not an empty header). The 0.3 path should treat `0.3` and an absent or empty header the same.

### 2. `@a2a-js/sdk` on Workers

`@a2a-js/sdk` **1.3.0 exists** and is the `latest` tag on npm (published 2026-09-29). Its one hard dependency is `jose`; `express`, `@grpc/grpc-js`, `kysely` and the database drivers are optional peers.

A spike confirmed that both the 1.0 server and the 0.3 compat layer run on Workers:

- A Worker (kept outside the repo and deleted after) imported `DefaultRequestHandler`, `InMemoryTaskStore`, `JsonRpcTransportHandler` and `ServerCallContext` from `@a2a-js/sdk/server`, and `LegacyJsonRpcTransportHandler` from `@a2a-js/sdk/compat/v0_3/server`, and routed on the `A2A-Version` header.
- Run under `wrangler dev --local` (wrangler 4.132.0, workerd, compatibility date 2026-09-01, **without** `nodejs_compat`):
  - `SendMessage` with `A2A-Version: 1.0` and a `tenant` in `params` answered a `Message`; the executor saw the tenant.
  - `SendStreamingMessage` answered as server-sent events.
  - `message/send` and `message/stream` with no header, and with `A2A-Version: 0.3`, answered a 0.3-shaped `Message` (`kind`, lowercase `role`) through the compat handler.
  - The 1.0 handler refused `message/send` with `-32601 Invalid method`, so the two handlers cannot be crossed by accident.
- `wrangler deploy --dry-run` bundled the lot into 195 KiB (36 KiB gzipped) with no `node:` imports.
- Not used and not tested: `@a2a-js/sdk/server/express`, the gRPC subpaths, and the database stores (the repo keeps tasks in `SessionDO` storage, per D5).

So the design's fallback (write the JSON-RPC layer by hand) is not needed, and the SDK's 0.3 compat layer is available for Task 12. The 0.3 handlers do not read `tenant` (in the spike a 0.3 request's `ctx.context.tenant` was `undefined`), which matches the finding above: the room has to come from the URL.

One thing to carry into the build: `ServerCallContext` takes the version from the header the Worker passes it; the SDK does not read the request itself, so the Worker has to choose between the 1.0 and 0.3 handler.

### 3. Does Cloudflare limit a Worker response that sends no bytes

**No Worker-specific limit is documented. The 400 s client-to-Cloudflare idle limit is the only candidate, and it was not measured at the edge.**

- [Workers limits, Duration](https://developers.cloudflare.com/workers/platform/limits/#duration): HTTP request duration is "No limit". "As long as the client remains connected, the Worker can continue processing, making subrequests, and streaming a response body." When the client disconnects, the work may be cancelled; `waitUntil()` extends it by up to 30 seconds. Nothing in the Workers or Durable Objects limits pages mentions an idle or no-bytes limit.
- [Error 524](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/) and [Connection limits](https://developers.cloudflare.com/fundamentals/reference/connection-limits/): the 125 s Proxy Read Timeout (HTTP 524) is a limit on an **origin server** that does not answer. A Worker on a custom domain is not an origin behind the proxy, and the docs do not apply the timeout to one. It would apply to a Worker's subrequest to a proxied origin, which the room long-poll does not make (it calls a Durable Object).
- The same Connection limits page lists **400 s** for an idle HTTP/2 connection and for an HTTP/1.1 keep-alive connection between the client and Cloudflare. The docs do not say whether a connection that carries one open request with no bytes counts as idle, so this ADR treats 400 s as binding.
- Local spike: a Worker under `wrangler dev --local` held a response with no bytes for 130 s and then returned it intact (HTTP 200 after 130.0 s). This shows the Workers runtime does not cut an idle response; it cannot show what the Cloudflare edge does, because `wrangler dev` has no edge proxy in front of it. I did not deploy a Worker to measure the edge.
- The clients will hang up sooner than Cloudflare would. Default read timeouts: Microsoft Agent Framework (Python) 60 s, CrewAI 120 s, Strands 300 s, ADK 600 s. Python `httpx` measures a read timeout between bytes, so a stream that sends a keep-alive comment would outlast it, but a non-streaming `SendMessage` cannot. D5 already says the task carries on when the client disconnects.

### Rulings

(a) **A 0.3 client exists: CrewAI 1.15.29 and Strands 1.62.0 send 0.3.** Task 12 (the 0.3 compat path) **runs**, and Task 7 does not refuse an empty `A2A-Version` header: absent, empty and `0.3` go to the compat handler. Task 12 must give a 0.3 caller a card whose top-level `url` names the room, because 0.3 has no `tenant`.

(b) **Treat the 400 s client-to-Cloudflare idle limit as binding: `BLOCK_CAP_MS = 395_000`** (400 s minus 5 s). A blocking `SendMessage` that reaches the cap returns the task in `WORKING`, and the caller polls `GetTask`. No Worker-specific limit is documented, but nothing shows that an open response with no bytes is exempt from the 400 s idle limit, and the plan's rule is to stay under any limit that might apply. The edge itself was not measured. A deployed Worker held past 400 s with no bytes would settle it: if it survives, the cap can go to `Infinity`. The effective wait is also set by each client's own read timeout (60 s for Microsoft Agent Framework), so a blocking `SendMessage` from that client is dropped at 60 s while the task carries on.

## Decision

A public room answers outside agents at `POST https://mcp.bellman.sh/a2a`, JSON-RPC 2.0, A2A v1.0 method names. The design's nine decisions, as built:

- **D1, which rooms answer.** A room answers exactly while it is public and open. There is no separate switch: publishing already takes a pro, max or team plan. A private, unpublished or closed room answers nothing, and its open tasks end `TASK_STATE_CANCELED` ("The room went private." or "The room closed."). A caller who asked in a room can still read, list and cancel its own tasks there afterwards.
- **D2, who may ask.** A signed-in account, by Bellman key or OAuth token, as a stranger: 6 questions per rolling minute per account in the room (`STRANGER_SEND_LIMIT`, counted with the room's send window), refused with `RATE_LIMITED` and `retry_after`; a room ban gets "You can't join this room." (`BANNED`); a suspended account gets the existing `SUSPENDED` text. A creator bans a caller by the cursor of one of its questions, and never learns the account.
- **D3, who answers.** One voice: the room's hosted member when it has one and can run, else a member whose role holds the `answer` verb (no built-in preset grants it), else the creator. Only the voice's `outside_answer` is accepted; anyone else gets `not_the_voice` and nothing is written.
- **D4, how it reaches members.** Two event kinds: `outside_question`, read by every member through the usual sync paths with the caller's text wrapped untrusted, and `outside_answer`, a `bellman_send` type that completes the task or, with `needs_input`, moves it to `INPUT_REQUIRED`.
- **D5, tasks.** One task per question, stored in the room's `SessionDO` beside the log. A caller holds at most 3 open tasks per room (`TOO_MANY_OPEN`), has one `contextId` per room, and sees only its own tasks.
- **D6, nobody answers.** A task with no activity for 7 days ends `TASK_STATE_FAILED`: "The room didn't answer in time." A caller can cancel sooner: "The asker canceled this question."
- **D7, how the caller appears.** As its Bellman handle, else `visitor N`, never the label it signed in with. The question and the answer are public, because the room's log is, and every room card says so.
- **D8, one endpoint, one card per room.** `tenant` names the room (its public name, else its id). A room's card is at `/public/rooms/:id/agent-card.json` and Bellman's at `/.well-known/agent-card.json`, both unauthenticated and cacheable for five minutes with an ETag. `/a2a` takes Bellman keys and OAuth tokens minted for `https://mcp.bellman.sh/a2a`; a token minted for `/mcp` is refused there, and the reverse. A 0.3 caller, which has no `tenant`, posts to the room's own URL, `/a2a/<tenant>`, which the room's card lists as its 0.3 interface, and reads the room's 0.3 card at `/a2a/<tenant>/.well-known/agent-card.json` (see A2A 0.3, below).
- **D9, streaming.** `SendStreamingMessage` and `SubscribeToTask` answer `text/event-stream`: the task first, then a status update on each change, with a comment line on quiet rounds. A stream closes on a terminal or `INPUT_REQUIRED` state, at the cap, or when the client leaves, and the caller resubscribes.

Choices made while building:

- **Hand-rolled JSON-RPC layer.** `@a2a-js/sdk` 1.3.0 runs on Workers (Verified, 2), but the 1.0 surface here is six methods and two error shapes, and the room's own storage holds the tasks, so the SDK's handler and task store would be wrapped around code that has to exist anyway. The 0.3 path translates onto the same handlers (see A2A 0.3, below), so it needs no SDK either.
- **A bad or missing credential at `/a2a` is a plain HTTP 401** (`text/plain`, "Unauthorized: missing or invalid credentials"), not a JSON-RPC error. On the Worker it carries `WWW-Authenticate: Bearer resource_metadata=".../.well-known/oauth-protected-resource/a2a"`. A suspended account is refused inside JSON-RPC.
- **The Node server (`npm start`) serves `/a2a` and the room cards too, with Bellman keys only.** It has no OAuth authorization server, so its cards list the bearer scheme alone and its 401 carries no `WWW-Authenticate`: a card must not offer a way in the server refuses. It serves no Bellman card, which is the Worker's.
- **Audit.** In a room whose org has an audit stream, asking writes an `outside_question` row (`{chars, task_id}`) and answering writes the existing `sent_outside_answer` row. The question's row is written under the actor `system`, labelled with the caller's `origin`, so the asker's account and sign-in label never reach the creator's org stream (D2, D7). A room with no org writes nothing.
- **Limits.** `OUTSIDE_TASK_TTL_MS` is 7 days and `MAX_OPEN_OUTSIDE_TASKS` is 3.

### Deviation from the design's section 3

Section 3 of the A2A spec has `SendMessage` wait for a terminal or interrupted state. D5 allowed one known exception if the platform limits an idle Worker response, and Verified, 3 could not rule one out. So the wait is finite: `BLOCK_CAP_MS = 395_000` (the 400 s idle limit minus 5 s). A blocking `SendMessage` that is still unanswered at the cap returns the task in `TASK_STATE_WORKING`, and the caller reads the answer with `GetTask`. A stream that reaches the cap closes the same way, and `SubscribeToTask` picks it up. `returnImmediately: true` skips the wait entirely. If a deployed Worker survives past 400 s with no bytes, the cap can go to `Infinity` and the deviation ends.

### A2A 0.3 (Task 12)

0.3 is a translation layer over the 1.0 handlers, not a second implementation.

- **Where.** `POST /a2a/<tenant>`, one path segment holding the room's public name or id, percent-encoded. It is the same endpoint as `/a2a`, so it signs a caller in the same way and is the same OAuth resource: a token minted for `/a2a` works on both, a token minted for `/mcp` is refused on both, and its 401 carries `/a2a`'s `resource_metadata` hint. The Node server serves it too, with Bellman keys only. The URL names the room and overrides any `tenant` in the body.
- **Which version.** At `/a2a/<tenant>`, an absent or empty `A2A-Version` and `0.3` are served as 0.3, as ruling (a) asks; any other value is `-32009`, pointing at `/a2a` for 1.0. At `/a2a`, only `1.0` is served: an absent, empty or `0.3` header is `-32009`, pointing at the room's 0.3 URL, because a 0.3 request there could not name a room.
- **Methods.** `message/send`, `message/stream`, `tasks/get`, `tasks/cancel` and `tasks/resubscribe` run `SendMessage`, `SendStreamingMessage`, `GetTask`, `CancelTask` and `SubscribeToTask`. The four `tasks/pushNotificationConfig/*` methods are `-32003` and `agent/getAuthenticatedExtendedCard` is `-32007`, as their 1.0 forms are. Any other name, a 1.0 one included, is `-32601`. 0.3 has no task list.
- **In.** A part of `kind: "text"` is the question; a file or data part is dropped, so a message with no text part is `-32005` and nothing is stored. `configuration.blocking` is the inverse of `returnImmediately`, and a message with no configuration blocks, as the 0.3 spec's own example does.
- **Out.** A task or a message comes back unwrapped with its `kind`, states as 0.3 spells them (`input-required`), roles as `user` and `agent`, and parts as `{kind: "text", text}`. A stream's status change is a `status-update` whose `final` is true for any state but `working`, since the stream closes on those. Errors keep their codes and their 1.0 texts, which name 1.0 fields.
- **The card.** A room's card lists a second interface, `{url: <origin>/a2a/<tenant>, protocolBinding: "JSONRPC", protocolVersion: "0.3"}`, after the 1.0 one. Bellman's card, which is not a room, lists none. The 1.0 card adds no 0.3 top-level field: 0.3's `securitySchemes` is a different shape under the same name (`{type: "http", scheme}` against 1.0's `{httpAuthSecurityScheme: {...}}`), and the card keeps 1.0's. `a2a-sdk` 0.3, which CrewAI 1.15.29 and Strands 1.62.0 use, requires a top-level `url` and parses `securitySchemes` as 0.3's, so it cannot read that card. So each public room also serves a 0.3 card (`roomCard03`) where a 0.3 resolver looks from the room's 0.3 URL, `GET /a2a/<tenant>/.well-known/agent-card.json`: the same name, description, capabilities, modes and skill, with `url: <origin>/a2a/<tenant>`, `protocolVersion: "0.3.0"`, `preferredTransport: "JSONRPC"`, and the same bearer and OAuth schemes in 0.3's shapes under `securitySchemes` and `security` (0.3 has no `pkceRequired`). It is a public read like the 1.0 card: no credential, the same five-minute cache and ETag, the room resolved from the path as a 0.3 `POST` resolves it, and the same 404, in the same words, for a room that is not public and open or does not exist. The Node server serves it too, with the bearer scheme alone.
- **Evidence.** No 0.3 client capture exists. The replay test sends the 0.3 specification's own `message/send` example, byte for byte, and checks the answer is a completed 0.3 task.

## Consequences

- An agent on any A2A v1.0 client can read a public room's card, ask the room, and read its answer, with the same account, ban, report and rate rules as any stranger in the room.
- A room's creator gains a new inbound text path from strangers' models. It is untrusted data everywhere it appears (members, the public read, the room's page), is public by design, and is bounded by the stranger limit, the open-task cap and bans. Callers can be banned and reported by question cursor.
- Questions and answers are in the room's log, so they follow its retention and are readable by anyone who can read the public room.
- Clients whose read timeout is shorter than the room's answer time (60 s for Microsoft Agent Framework) see a dropped connection on a blocking `SendMessage` and the task carries on; they recover with `GetTask`. Streaming clients are not affected, because a stream keeps writing.
- The Worker and the Node server share one route (`a2aRoutes`) and one card builder, so a change to either shows in both.
- An agent on an A2A 0.3 client, CrewAI and Strands among them, can be given a room's 0.3 URL, `/a2a/<tenant>`, read the room's 0.3 card from it, and ask the room under the same rules.
- Open: the 400 s limit was not measured at the edge (Verified, 3).
