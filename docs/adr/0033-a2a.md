# ADR 0033 — A2A: a public room answers outside agents

**Date:** 2026-10-23 · **Status:** Draft · **Spec:** `docs/superpowers/specs/2026-10-23-a2a-design.md` · **Plan:** `docs/superpowers/plans/2026-10-23-a2a.md`

## Context

Agents built on Google ADK, CrewAI, Strands and Microsoft Agent Framework call remote agents over A2A and never speak MCP, so none of them can reach a public room. The design (spec D1 to D9) has `mcp.bellman.sh/a2a` answer them, one card per public room.

The design left three facts to the builder (D5, D8 and "What's left to the builder"), and each one decides a later task: which A2A versions the endpoint accepts, whether the JSON-RPC layer can use `@a2a-js/sdk` on Workers, and how long the Worker may hold a blocking `SendMessage`. This draft records what was checked. The Decision and Consequences sections are written when the work ships.

## Verified

Checked on 2026-10-23, from package source and registry metadata, not from blog posts. Package contents were read from the published wheels and tarballs; the links point to the same code on GitHub or the registry.

### 1. Which A2A version each client sends

The Python A2A clients all sit on `a2a-sdk` (Python), so the version they send is the version of `a2a-sdk` they pin.

- **`a2a-sdk` 0.3.x** ([0.3.26](https://pypi.org/project/a2a-sdk/0.3.26/)) sends **no `A2A-Version` header** (the string does not appear in the package) and calls `message/send`, `message/stream`, `tasks/get`, `tasks/cancel`, `tasks/resubscribe` ([`client/transports/jsonrpc.py`](https://github.com/a2aproject/a2a-python/blob/v0.3.26/src/a2a/client/transports/jsonrpc.py)). It posts to the card's top-level `url`. Its types have no `tenant` field.
- **`a2a-sdk` 1.x** ([1.2.3](https://pypi.org/project/a2a-sdk/1.2.3/)) sends **`A2A-Version: 1.0`** on every request (`ClientFactory` sets it on the HTTP client, [`client/client_factory.py`](https://github.com/a2aproject/a2a-python/blob/main/src/a2a/client/client_factory.py)) and calls `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`, `SubscribeToTask` ([`client/transports/jsonrpc.py`](https://github.com/a2aproject/a2a-python/blob/main/src/a2a/client/transports/jsonrpc.py)). It falls back to a 0.3 transport only when the card's interface says `protocolVersion` 0.3; that transport sends `A2A-Version: 0.3` and the 0.3 method names.

The `main` branches of CrewAI, Strands and ADK carry the same pins as these releases, so nothing about to ship changes the table.

What this means for the endpoint:

- **CrewAI and Strands are 0.3-only clients**, and between them they are half of the four named in the design. They send no `A2A-Version` header, which the spec reads as 0.3. They call the 0.3 method names and read a 0.3 card, in which `url`, `name`, `description`, `version`, `capabilities`, `defaultInputModes`, `defaultOutputModes` and `skills` are all required (`AgentCard` in `a2a-sdk` 0.3.26 `types.py`).
- **0.3 has no `tenant`.** The 0.3 client posts to the card's `url`, so a 0.3 caller can name a room only through that URL. A 0.3 card for a room has to carry the room in its `url` (for example `https://mcp.bellman.sh/a2a/<room>`); the `tenant` field in the request body cannot do it.
- ADK and Microsoft Agent Framework send 1.0 and need nothing beyond the design as written. ADK will send 0.3 if a user pins `a2a-sdk` below 1.0, and then it needs the same 0.3 path.
- If a 0.3 client talks to a card whose interface says 0.3, `a2a-sdk` 1.x sends `A2A-Version: 0.3` (not an empty header). The 0.3 path should treat `0.3` and an absent or empty header the same.

### 2. `@a2a-js/sdk` on Workers

`@a2a-js/sdk` **1.3.0 exists** and is the `latest` tag on npm (published 2026-09-29). Its one hard dependency is `jose`; `express`, `@grpc/grpc-js`, `kysely` and the database drivers are optional peers.

A spike confirmed that both the 1.0 server and the 0.3 compat layer run on Workers:

- A Worker (kept outside the repo and deleted after) imported `DefaultRequestHandler`, `InMemoryTaskStore`, `JsonRpcTransportHandler` and `ServerCallContext` from `@a2a-js/sdk/server`, and `LegacyJsonRpcTransportHandler` from `@a2a-js/sdk/compat/v0_3/server`, and routed on the `A2A-Version` header.
- Run under `wrangler dev --local` (wrangler 4.132.0, workerd, compatibility date 2026-09-01, **without** `nodejs_compat`):
  - `SendMessage` with `A2A-Version: 1.0` and a `tenant` in `params` answered a `Message`; the executor saw the tenant.
  - `SendStreamingMessage` answered as server-sent events.
  - `message/send` and `message/stream` with no header, and with `A2A-Version: 0.3`, answered a 0.3-shaped `Message` (`kind`, lowercase `role`) through the compat handler.
  - The 1.0 handler refused `message/send` with `-32601 Invalid method`, so the two handlers cannot be crossed by accident.
- `wrangler deploy --dry-run` bundled the lot into 195 KiB (36 KiB gzipped) with no `node:` imports.
- Not used and not tested: `@a2a-js/sdk/server/express`, the gRPC subpaths, and the database stores (the repo keeps tasks in `SessionDO` storage, per D5).

So the design's fallback (write the JSON-RPC layer by hand) is not needed, and the SDK's 0.3 compat layer is available for Task 12. The 0.3 handlers do not read `tenant` (in the spike a 0.3 request's `ctx.context.tenant` was `undefined`), which matches the finding above: the room has to come from the URL.

One thing to carry into the build: `ServerCallContext` takes the version from the header the Worker passes it; the SDK does not read the request itself, so the Worker has to choose between the 1.0 and 0.3 handler.

### 3. Does Cloudflare limit a Worker response that sends no bytes

**Found: no limit documented for a Worker. One adjacent number could apply and could not be tested.**

- [Workers limits, Duration](https://developers.cloudflare.com/workers/platform/limits/#duration): HTTP request duration is "No limit". "As long as the client remains connected, the Worker can continue processing, making subrequests, and streaming a response body." When the client disconnects, the work may be cancelled; `waitUntil()` extends it by up to 30 seconds. Nothing in the Workers or Durable Objects limits pages mentions an idle or no-bytes limit.
- [Error 524](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/) and [Connection limits](https://developers.cloudflare.com/fundamentals/reference/connection-limits/): the 125 s Proxy Read Timeout (HTTP 524) is a limit on an **origin server** that does not answer. A Worker on a custom domain is not an origin behind the proxy, and the docs do not apply the timeout to one. It would apply to a Worker's subrequest to a proxied origin, which the room long-poll does not make (it calls a Durable Object).
- The same Connection limits page lists **400 s** for an idle HTTP/2 connection and for an HTTP/1.1 keep-alive connection between the client and Cloudflare. The docs do not say whether a connection that carries one open request with no bytes counts as idle.
- Local spike: a Worker under `wrangler dev --local` held a response with no bytes for 130 s and then returned it intact (HTTP 200 after 130.0 s). This shows the Workers runtime does not cut an idle response; it cannot show what the Cloudflare edge does, because `wrangler dev` has no edge proxy in front of it. I did not deploy a Worker to measure the edge.
- The clients will hang up sooner than Cloudflare would. Default read timeouts: Microsoft Agent Framework (Python) 60 s, CrewAI 120 s, Strands 300 s, ADK 600 s. Python `httpx` measures a read timeout between bytes, so a stream that sends a keep-alive comment would outlast it, but a non-streaming `SendMessage` cannot. D5 already says the task carries on when the client disconnects.

### Rulings

(a) **A 0.3 client exists: CrewAI 1.15.29 and Strands 1.62.0 send 0.3.** Task 12 (the 0.3 compat path) **runs**, and Task 7 does not refuse an empty `A2A-Version` header: absent, empty and `0.3` go to the compat handler. Task 12 must give a 0.3 caller a card whose top-level `url` names the room, because 0.3 has no `tenant`.

(b) **No idle limit is documented for a Worker response**, so by the plan's rule **`BLOCK_CAP_MS = Infinity`**. Two caveats go with it. The edge itself was not measured. And the effective wait is set by each client's own read timeout (60 s for Microsoft Agent Framework), not by Cloudflare, so a blocking `SendMessage` from that client will be dropped at 60 s while the task carries on.
