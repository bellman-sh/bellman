# SSO: Per-Org OIDC, Domain Verification and JIT Provisioning — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An org's admin configures one OIDC identity provider and proves their email domains by DNS; a sign-in is routed to that provider by its email's domain, provisions the person into the org on first use, and `require_sso` closes the GitHub and Google doors to everyone in the org but its owner.

**Architecture:** One generic OIDC provider, configured per org and discovered when saved (`src/oauth/oidc.ts`), its client secret sealed with a Worker secret (`src/oauth/sealed.ts`), stored in `RegistryDO` under `oi:<orgId>` apart from the `Org` record; domain claims on the record with a global `od:<domain>` index written only at verification (`src/oauth/dns.ts` resolves the TXT record over DNS-over-HTTPS). The sign-in pages gain a work-email field whose domain picks the IdP; `/callback/sso/:orgId` turns the IdP's id token into a `ProviderProfile` with `provider: "sso"` and runs the same tail as GitHub. Enforcement is one predicate, `ssoRefusal`, asked where plans resolve, so a token or panel session from before the switch stops at its next re-check.

**Tech Stack:** TypeScript, Web Crypto (HKDF, AES-GCM, SHA-256), fetch (OIDC discovery, token and userinfo endpoints; Cloudflare DNS-over-HTTPS JSON), vitest over `MemoryStore` plus the worker program for the store contract.

**Spec:** `docs/superpowers/specs/2026-10-21-orgs-and-sso-design.md`, decisions D9 to D14, on top of PR 1 (D1 to D8, plan `2026-10-21-orgs.md`, ADR 0023).

## Global Constraints

- Every `BellmanStore` method is async and joins `tests/helpers/store-contract.ts`; a guarded write is one operation (synchronous in `MemoryStore`, one `ctx.storage.transaction` in `RegistryDO` with audit rows queued inside it).
- The identity key is `sso:<orgId>:<sub>`; the user id is `u_sso_<base64url(orgId + ":" + sub)>`; `sub` is 1 to 128 printable ASCII characters (`/^[\x21-\x7e]{1,128}$/`) (D10).
- An IdP issuer is an https URL with no query or fragment; the authorization and token endpoints must be https; the discovery document's `issuer` must equal the one given (D9).
- The id token is read without a signature check (OIDC Core 3.1.3.7 step 6: received directly from the token endpoint over TLS); `iss`, `aud`, `exp`, `nonce` and `sub` are checked (D12). The nonce is the SHA-256 (base64url) of the state token.
- The client secret is stored only sealed: `v1.<nonce>.<ciphertext>`, AES-256-GCM, key = HKDF-SHA256(`BELLMAN_SEAL_SECRET` or else `BELLMAN_TOKEN_SECRET`, info `bellman:org-idp-secret`); no route ever returns it (D14).
- A domain is lowercased, matches `/^(?=.{1,253}$)([a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?\.)+[a-z]{2,63}$/`; the TXT record is `_bellman.<domain>` with value `bellman-verify=<token>`, the token 16 random bytes base64url (D11).
- `require_sso` needs an IdP and at least one verified domain (D13); the owner, an operator override and an SSO profile are exempt from it.
- Never "two sessions"; `npm run verify` green before the PR; the docs-site build green.

## Review Focus

1. An email whose domain is claimed but not yet verified must route nowhere and verify nothing for the org: the `od:` index is written only at verification — Task 5 pins it in the contract.
2. An `aud` claim that is an array containing the client id passes; one that is another client's id fails, and so does a token whose `iss` differs by a trailing slash — Task 3 pins it.
3. A second SSO sign-in by the same `sub` provisions nothing and resolves to the role an admin set since (`exists` keeps the grant) — Task 7 pins it.
4. A GitHub sign-in whose verified address is under a `require_sso` org's domain is refused even with no grant anywhere, and the owner's GitHub sign-in is admitted under the same conditions — Task 7 pins it.
5. A DNS answer with several TXT strings, quoted and split (`"bellman-" "verify=abc"`), or with the record among other TXT records, verifies; a DoH 5xx is `502 dns`, never "unverified" — Task 4 pins it.
