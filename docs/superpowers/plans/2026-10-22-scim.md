# SCIM Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An IdP's provisioning connector can push, update and deactivate an org's members over SCIM 2.0 with a per-org token, and a deactivation ends the person's sign-in, frees their seat, takes them out of every room and freezes the rooms they created.

**Architecture:** SCIM users are rows in `RegistryDO` beside the grants they name (`su:`), with a per-org directory by address (`sn:`) and an index by key (`sk:`) that the SSO sign-in and `moveGrant` keep current; the routes in `src/http/scim.ts` authenticate by a hashed token (`sc:`/`sh:`), write through guarded store methods that audit in the same transaction, and run the room pass (`src/scim/rooms.ts`) after the registry answers. Sign-in refusal of a deprovisioned subject rides the `SsoRequired` path, generalised to `SignInRefused`.

**Tech Stack:** TypeScript, Cloudflare Workers + Durable Objects (`RegistryDO`), `MemoryStore`, vitest, workerd tests under `worker-tests/`, WebCrypto (SHA-256).

**Spec:** `docs/superpowers/specs/2026-10-22-scim-design.md`

## Global Constraints

- Every `BellmanStore` method is async; every registry decision is one transaction with its audit intents enqueued inside it (`this.driver.enqueue(txn, this.#auditIntents(...))`, then `deliverNow()` on success); writers are `#private` (CLAUDE.md, ADR 0006).
- Workers-only files (`src/store-do.ts`) are out of the Node build and no vitest test imports them: rules live in runtime-free modules (`src/grant-index.ts`, `src/grant-audit.ts`, `src/scim/*`).
- Both stores pass `tests/helpers/store-contract.ts` identically; it runs under vitest and under workerd (`worker-tests/store-contract.test.ts`).
- Copy: "members", "the room", "peers"; never "two sessions" or "the other session". No new MCP tool, so no manifest or docs:gen change.
- Keys: `su:<orgId>:<id>`, `sn:<orgId>:<address>`, `sk:<key>`, `sc:<orgId>`, `sh:<tokenHash>`; org ids pass `isOrgId`, so `su:<orgId>:` is a safe prefix.
- SCIM copy: responses `application/scim+json`; the error schema `urn:ietf:params:scim:api:messages:2.0:Error` with `status` as a string, `detail`, `scimType` when one applies; `userName` lowercased whole and containing `@`; a token is `bst_` + base64url of 32 random bytes; `count` at most 200; a body at most 16 KB; the list scan capped at 1,000 rows.
- Audit actor for SCIM writes: `{ actorUserId: "scim", actorLabel: "SCIM", actorOrgId: orgId }`; user rows under `sessionId: "scim:<id>"`, token rows under `org:<orgId>`.
- `main` moves by PR; commit after each task with `npm run verify` green (and `npm run typecheck:worker` for a task that touches `src/store-do.ts`).

## Review Focus

1. **A token's hash collides with nothing but itself**: a token for org A presented after org B issued one must resolve to A, and a revoked token must resolve to nothing even if its hash row was the newest (Task 2's contract test covers replace and revoke; the route test in Task 6 presents a stale token after rotation and expects 401).
2. **A SCIM id of another org**: `GET /scim/v2/Users/<id of org B>` with org A's token is 404, never 200 or 403 (Task 6 test "another org's id is a stranger").
3. **`PATCH` with `active: "False"` from Entra and `{op: "replace", value: {active: false}}` from Okta both deactivate**, and a `PATCH` naming only `emails` changes nothing and answers 200 (Task 5's patch tests pin all three).
4. **Deprovisioning a person with no sign-in yet** (key `email:`) removes the grant and runs no room pass, and does not throw on `userIdForKey` returning null (Task 6 test "an address nobody claimed has no rooms").
5. **A re-sent deactivation** of an already inactive user answers 200, writes no second `plan_revoked`, and runs the room pass again, which finds nothing left to do (Task 6 test "a repeat is harmless").

- Produces, on `BellmanStore`:
  ```ts
  /** One transaction (spec D5). `user.key` is what the caller proposes (`email:<userName>`); the stored row's key is what the directory or an existing grant said. */
  createScimUser(user: ScimUser, audit: AuditIntent): Promise<{ outcome: "written" | "linked"; user: ScimUser } | { outcome: "exists" | "conflict" | "full" | "no_org" }>;

  /** One transaction (spec D6 to D8). `was` is the row before; a deactivation deletes the grant at `was.key` when it is this org's, a reactivation writes it again as a member, a rename moves an `email:` grant and the directory row. */
  ```
