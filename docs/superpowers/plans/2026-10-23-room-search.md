# Room Search Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This plan runs with subagents and **one whole-branch review per PR, at the end**: no per-task review steps, whatever a skill says.

**Goal:** Whoever may read a room can search it: an agent through `bellman_surface` with `query` (and `in: "messages"` for the log), a person through a search box on the room's public page and in the dash. A search reads one room, writes nothing, and answers at most ten pointers (a card's key, title, snippet, date, author, approver and URL; a message's cursor, sender, snippet and time) with the count of all that matched.

**Architecture:**
- **Part 1, the server.** `src/search.ts` (runtime-free) normalises, matches, ranks and cuts snippets for cards and messages. `src/projections.ts` gives a hit its wire shape in the surface read's envelope. `src/rooms.ts` composes read and search once, and the tool and the four reads call it. No store method, tool or limit is added.
- **Part 2, the dash.** A search box on the public page and in the members' room view: cards over the canvas and Page views, messages over the Log. The query is the `q` search parameter; the list renders what the server answered.

**Tech Stack:** TypeScript. bellman: Cloudflare Workers and Durable Objects, zod, vitest 5 for the root program. The dash: Vite 8, React 19, TanStack Router, vitest 5.

**Spec:** `docs/superpowers/specs/2026-10-23-room-search-design.md` (approved 2026-10-23). It builds on `2026-10-22-topic-rooms-design.md`, `2026-10-18-room-pages-design.md` and `2026-10-17-public-rooms-on-bellman-sh-design.md`.

## Global Constraints

- **Writing.** A room holds many members: never a phrase that counts the room as a pair of sessions or names one peer as its only other one; say members, the room, or peers. Never a phrase the word scan of Task 5, Step 4 searches for (its pattern is the list), in code, comments, docs, commit messages or the PR. This plan spells the list only as that pattern, so a scan of the plan itself passes.
- **The search (D1, D5).** One room's rows or log; case-insensitive; every word must appear; a title match above a body or key match, then newest first (`created_at`, or cursor); ten results and `total`; a query of 3 to 200 characters.
- **The bounds (D8).** At most 64 cards. A member's message search scans the last 2,000 events; the public's the newest 200. No limiter, cache or new limit.
- **No new tool (D4).** `bellman_surface` gains `query` and `in`; `extension/manifest.json` stays as it is, and `tests/extension.test.ts` keeps passing.
- **A search writes nothing.** No event, no row, no audit row, no `lastSeenAt`. Task 2 pins it.
- **Store methods** are async, every one, and a new one goes into `MemoryStore`, the Durable Objects store and `tests/helpers/store-contract.ts`. This plan adds none (R13).
- **Untrusted text stays untrusted.** A snippet and a title are peer content: the tool returns each result inside the envelope the surface read uses (`untrusted(origin, data)`), the page renders them as text, and the HTTP reads escape nothing, because JSON is not HTML.
- **Generated files.** `src/ui/assets.ts` is generated by `npm run build:ui`: edit `ui/`, never it. `plugin/bridge/*.mjs` are rebuilt only by release PRs, and neither PR here is one. The docs site's tool pages are written by `npm run docs:gen` and pinned by `tests/docs-reference.test.ts`; never edit them by hand. A tool text change means `docs:gen` and a new measurement in ARCHITECTURE section 11.
- **Non-ASCII in TypeScript** is a braced escape: U+00B7 is `\u{B7}`, U+2026 is `\u{2026}`. JSX text reads no escape, so there it goes in a string expression: `{" \u{B7} "}`.
- **Tools.** Edit files with the Edit or Write tool, never `perl -i` or `sed -i`. Never call a `graph_*`, dual-graph or `bellman_*` tool. Never bypass commit signing: a commit that hangs or says "incorrect passphrase supplied" is a stop, reported to the lead.
- **Reviews.** One whole-branch review per PR, after its last task. No task has a review step.
- **Repos.** bellman is jj (`jj commit`); the dash is git, on a branch from `origin/main`. Every commit is signed. Nothing reaches `main` but through a PR.
- **Order.** Part 1 starts after topic rooms' server PR merges. Part 2 starts after Part 1 deploys and after room pages' dash PR (Part 2) and topic rooms' dash PR have merged and deployed.

## Rulings

Where the spec is silent, or the code disagrees with it, and what this plan does. **★** marks a ruling that goes beyond the spec's letter.

- **R1. The pure module is `src/search.ts`,** runtime-free beside `src/surface.ts`, importing types and `createdAtOf` only. Its exports (Task 1's Interfaces) are the one place a record is matched, ranked or cut: the tool and the four reads reach them through `src/rooms.ts` (R12), and the dash ranks nothing.
- **R2. ★ Normalising.** `queryWords(query)`: `toLowerCase()`, split on `/\s+/`, then each word loses any run of characters at its start or end that are neither a letter nor a digit (`/^[^\p{L}\p{N}]+|[^\p{L}\p{N}]+$/gu`), and a word left empty is dropped. Characters inside a word stay (`node.js`, `a.b*`). Order kept, repeats kept. No stemming.
- **R3. ★ The length is the trimmed query's `.length`** (UTF-16 units, as every surface bound counts), 3 to 200. A query that passes the length but has no word left after R2 (`"..."`, `"-- --"`) is refused, since every word of nothing appears in every card. Refusals, verbatim: `query must be 3 to 200 characters`; `query must hold a word of letters or digits`.
- **R4. ★ A word matches as a substring** of the lower-cased field (`String.prototype.includes`): no regex, so a metacharacter is a character, and no word boundary, so `retry` finds `retries`. "Every word appears somewhere" is per word: each word in any one of the record's fields.
- **R5. The searched fields by kind (section 2).** `connector`: title. `file`, `image`: title and `blob.name`. Every other kind: title, body and key; an `html` item stored as a blob has no body, so title and key. A null field is no text.
- **R6. Order.** A card is rank 1 when every word is in its title, else rank 2; cards sort by rank, `createdAtOf(row)` descending, then key ascending by code units (`pageItems`' tie order). A message has no title, so messages sort by cursor descending, which never ties.
- **R7. ★ The snippet,** for the first query word `w` (section 2's "first query word"). The source is a card's body (none for a connector, a `file` or an `image`, whose body is not searched) or a message's text:
  1. the first line of the source (split on `\n`) whose lower-cased form holds `w`, trimmed, then `cutAtWord`;
  2. otherwise the title, trimmed and cut, when it is not null or blank (the spec's "the title when the match is in the title alone");
  3. otherwise a `file`'s or `image`'s `blob.name`, cut;
  4. otherwise the first non-blank line of the source, trimmed and cut (a match by key alone);
  5. otherwise null.

  A message always holds `w` in its text, so its snippet is never null. `cutAtWord(line)`: a line of 200 or fewer characters is itself; a longer one is cut at the last space at or before index 200 (`line.lastIndexOf(" ", 200)`), or at 200 when that finds none at an index above 0, and gains `\u{2026}`. So a snippet is at most 201 characters, the ellipsis included, and "about two hundred characters at a word" is exactly this; it is the rule the dash's `firstParagraph` cuts with. A body with no newline is one line. Whitespace inside a line is kept.
- **R8. ★ Which events are messages.** `isMessage(e)`: `e.type === "message" && e.fromMemberId !== "system"`, a member's or the hosted seat's (`m_host`). Its text is `payload.text` when that is a string, which members and the hosted seat send (`{ text }`, `{ kind, text }`); any other payload has no text and matches nothing. The payload is free-form, so this names the field the spec's "its text" means.
- **R9. The result shapes (D6, D7).** Each result is `untrusted(origin, data)`, the envelope `surfaceItem` and the events read use, with the author (a card) or the sender (a message) as `origin`, the same `{ memberId, label }` those reads put there. The sender is the origin and nothing else: `data` carries no `from`.

  ```ts
  // src/projections.ts
  type Origin = { memberId: string; label: string };
  export type CardResult = { trust: "untrusted"; origin: Origin; data: {
    key: string; kind: SurfaceKind; title: string | null; snippet: string | null;
    created_at: string;                                     // ISO, createdAtOf(row)
    approved_by: { member_id: string; label: string } | null; // as surfaceItem
    url: string | null;                                     // R11
  } };
  export type MessageResult = { trust: "untrusted"; origin: Origin; data: { cursor: number; snippet: string; at: string } };
  ```

  `approved_by` is built by one function, `approvedByOf(row)`, which `surfaceItem` is changed to call too.
- **R10. Names.** A member read names the author, approver and sender by the stored label, as `surfaceItem` and the events read do. A public read passes its answer through `numbered`, whose `byNumber` renames every `label` that holds a member's label (the origin's, `approved_by`'s) to `member N` or `host`; no other `data` field is named `label`, so a snippet is never renamed. The dash swaps the creator's number for `@handle` with `relabel`.
- **R11. `url`** is `cardUrl(session, key)` (`src/rooms.ts`): `${roomLink(session)}/${key}`, where `roomLink(s)` is `isPublic(s) ? publicRoomUrl(s) : null`, and null for a private room. `publicRoomUrl` writes `PUBLIC_ROOM_URL_BASE` and the room's held name, else its id: the spec's `https://bellman.sh/r/<room>/<key>`. A member searching a public room gets it too.
- **R12. One composition, in `src/rooms.ts`** (Task 2's Interfaces). `surfaceAt` is `readSurface`'s rows-and-cursor half, which `readSurface` then calls; `searchSurface` is `surfaceAt`, `searchCards`, `cardResult`; `memberLog` reads a member's window (R13); `searchLog` is `searchMessages`, `messageResult` and `searched` (R15). The tool and the four reads call these and nothing below them.
- **R13. ★ The member bound reads through `recentEvents`, which exists.** `memberLog` with no cut is `recentEvents(sessionId, MAX_MESSAGE_SCAN)`; under a removed member's cut it is `eventsAfter(sessionId, Math.max(0, cut - MAX_MESSAGE_SCAN), MAX_MESSAGE_SCAN)` filtered to `e.cursor <= cut`, the read `readEventsRoute` makes for the same member. Both methods are in both stores and the contract, so no store method is added. In Durable Objects `recentEvents` is one reverse `storage.list` with a limit, and the 2,000 events cross RPC to the Worker. A `ponytail:` comment on `MAX_MESSAGE_SCAN` names the ceiling (2,000 events of up to `MAX_PAYLOAD_CHARS`, 20,000, each can pass the RPC message limit) and the upgrade (a store method that matches inside the room's object, where an index would live).
- **R14. The public bound** is `recentEvents(id, MAX_EVENTS_READ)`, the newest 200, what the public events read takes with no `after`. `publicReadEvent` changes only `brief_update` and `member_joined`, so messages are searched off the 200 directly.
- **R15. ★ `searched: { events, from_cursor }`.** `events`: how many events the bound read, of every type, after a cut's filter. `from_cursor`: the oldest one's cursor, or null when it read none. A log shorter than the bound reads whole, so `from_cursor` is its first cursor, 1. Messages only.
- **R16. The tool.** Order: the room id (`NEED_ROOM`); the seat (`NO_SEAT`, so a caller with no seat is answered as today whatever it asks); `in` without `query`, refused verbatim `in needs query: send the words to search for, or leave in out to read the surface`; `checkQuery`. With `query` the answer is `{ query, in, total, results }`, plus `searched` for messages: `query` as sent, `in` `"cards"` when left out, and no `surface`, `session_id`, `your_seats` or `room`. The cut is `cutFor(mine)`; the text keeps `UNTRUSTED_PREAMBLE`. Without `query` and `in`, the answer is today's.
- **R17. ★ `_meta` stays.** `APP_UI_META` is on the tool's definition, not on a result: MCP Apps binds a resource to a tool, with no per-call way to drop it. A search answer has no `surface` key, so `pickScreen` (`ui/src/screen.ts`) gives it the `none` screen, which stops the canvas poll and shows the answer's text: no canvas, the spec's "shows nothing". `ui/` does not change; Task 2 pins `pickScreen`'s answer.
- **R18. ★ The HTTP shapes.** Both surface reads with `?query=` answer `{ surface_cursor, total, results: CardResult[] }`; both events reads `{ total, results: MessageResult[], searched }`, with no `cursor`: a search is not a page of the log, and a Log poll that took its cursor would skip events it never showed. No `in` over HTTP: the surface reads search cards, the events reads messages (D4).
- **R19. The HTTP refusals** are 400 `{ error: "invalid_request", error_description }`: R3's texts, and for `after` with `query`, verbatim, `after and query cannot be used together: a search reads the newest events, not a page past a cursor`. A present parameter is checked, so `?query=` is refused by length. Order: the caller and the room (401, 404; a public read's 404 first of all), `after`'s format, `after` with `query`, the query.
- **R20. ★ The validator.** A plain surface read's ETag stays `"<cursor>"` (`surfaceTag`). A search's is `searchTag(cursor, roomLink(session), words)`:

  ```ts
  export const searchTag = (cursor: number, link: string | null, words: readonly string[]): string =>
    `"${cursor}:${encodeURIComponent(link ?? "")}:${encodeURIComponent(words.join(" "))}"`;
  ```

  A private room's search for "Retry policy" at cursor 12 is `"12::retry%20policy"`; a public room named `mcp` gives `"12:https%3A%2F%2Fbellman.sh%2Fr%2Fmcp:retry%20policy"`. No two reads share a tag, so a stored ETag answers only the read it came from. The link is in it because `url` follows the room's name and whether it is public, which change without the cursor; the words are the normalised ones, since two spellings of one query answer alike. `encodeURIComponent` leaves no `"` or `,`, so `etagMatches`' comma split reads the tag whole. A search answers 304 on a match by the two paths a plain read takes (the record's cursor with no cut, the derived cursor under one).
- **R21. Nothing is written.** A search reads through `getSession`, `handlesOf`, `surfaceOf`, `recentEvents` and `eventsAfter` alone, and writes no audit row, as the plain reads write none.
- **R22. The texts.** `bellman_surface`'s description gains one sentence (Task 5) and its input `query` and `in`. `extension/manifest.json` keeps its one-line description; the tool list is unchanged.
- **R23. The ADR is numbered at the PR:** `docs/adr/00NN-room-search.md`. 0031 (org policy, #315) and 0032 (topic rooms, #317) are on `main`, so this is 0033 unless another PR lands first. Number against `origin/main`, every open PR and every local branch (`git for-each-ref` over `docs/adr`) when the PR opens.
- **R24. ★ The dash keeps the query in the URL, as `q`,** on `/r/$roomId` and `/rooms/$roomId`: the views are search parameters there already, so a search is a link to share, the back button undoes it and a reload keeps it. `validateSearch` keeps a `q` whose trimmed length is 3 to 200 and drops any other, so a bad link shows the view and no error. The box sets `q` on submit only, never per keystroke, since the public reads have no limiter; an empty submit removes it. The view tabs link without `q`, so switching tabs clears the search: each tab searches a different thing.
- **R25. ★ What owns what.** `src/components/room/search.tsx` holds `SearchBox`, `CardResults` and `MessageResults`; `PublicRoom` and `RoomDetail` place them. The box sits between the view tabs and the body, for cards on the canvas and Page views and for messages on the Log; while `q` is set, the results list takes the body's place. The box is one `<form role="search">` with `<input type="search" minLength={3} maxLength={200}>`: native bounds, no client-side matching.
- **R26. The public page calls the server's public reads directly,** at `API_ORIGIN` with `credentials: "omit"`, as `getPublicSurface` does. The dash's Worker does not change: it writes a page's head and summary from the path, so `?q=` gets the same page, whose script then searches.
- **R27. ★ What a result renders.** A card: its title (`titleOf`, its parameter widened to the three fields it reads) as an `<h2>` link, then `cardCredit` on one line, then the snippet as a `<p>` when not null. On the public page the title links in-app to `/r/$roomId/$itemKey` with the key the page was opened by, as `Article` does, which is the result's `url` on bellman.sh. In the members' view it is `<a href={url}>`, or plain text when `url` is null: a private room's card has no page. A message: `#<cursor>`, the sender's label, the time as `LogList` shows it, and the snippet. Every string is React text, never markup.
- **R28. ★ The lines above a result list, exact:** `cardsLine(total, shown)`: `No card matches.` · `1 card matches.` · `3 cards match.` · `14 cards match; the first 10 are shown.` `messagesLine(total, shown, scanned)`: the same with `message`, then ` Searched the newest <scanned> event(s).`: `No message matches. Searched the newest 200 events.` · `1 message matches. Searched the newest 1 event.` Numbers are written with `String(n)`, no locale. The empty state is the line with no list under it.
- **R29. The public rooms guide describes the page's box after Part 2 deploys** ("After this plan"). Part 1's docs describe what Part 1 ships: the tool and the four reads.

## Review Focus

The inputs most likely to bite a person using this, each pinned in the task named.

1. **A query of only punctuation** (`"..."`). Expected: refused, `query must hold a word of letters or digits`, never an answer listing every card. Task 1 and Task 2 (and the reads, Tasks 3 and 4).
2. **A word only in a card's key.** Expected: a rank 2 match, snippet the title, else the body's first line, else null; a `file` or `image` is not matched by key. Task 1.
3. **A public room whose match is older than its newest 200 events.** Expected: `total: 0`, and `searched` says it read 200 events from the 200th-newest cursor. Task 4.
4. **A message search by a member whose seat was removed.** Expected: nothing after the cut, though a later match is inside the 2,000; `searched` ends at the cut. Task 2 and Task 3.
5. **A plain poll's ETag sent with a search, a search's with a plain poll or another query.** Expected: 200 with the body asked for, never a 304. Task 3 and Task 4.

- [ ] **Step 2: The ADR**

````markdown
# ADR 00NN — Room search

**Date:** 2026-10-23 · **Status:** accepted · **Spec:** `docs/superpowers/specs/2026-10-23-room-search-design.md` · **Plan:** `docs/superpowers/plans/2026-10-23-room-search.md`

## Context

A topic room or a long-lived hub becomes a knowledge base of sixty cards and thousands of messages. An agent asked "what did we decide about X" had to read the whole surface, and a reader of a public page had to scroll it. Nothing let either ask the room a question and cite the answer.

## Decision

1. **A search is one room's read** (spec D1). It names a room and a query, reads that room's rows or log, writes nothing, and is answered by the reads a caller already has: `bellman_surface` with `query` and `in`, and `?query=` on `GET /rooms/:id/surface|events` and `GET /public/rooms/:id/surface|events`. No tool, store method or limit is added (D4, D8).
2. **Keyword matching, ranked, in one module** (D5). `src/search.ts` lower-cases, splits on whitespace and trims punctuation at a word's edges; every word must appear, as a substring, in a card's title, body or key (a connector's title; a file's or image's title and name) or a message's text. A title match ranks first; then newest; then key. Ten results and the count of all. The tool and the four reads call it through `src/rooms.ts`, so nothing ranks twice.
3. **Results are pointers in the surface read's envelope** (D6, D7): a card's key, kind, title, snippet, `created_at`, approver and page URL in a public room; a message's cursor, snippet and time; the author or sender as the envelope's origin, named as each read names members.
4. **Who may search is who may read** (D3). A member searches through the member reads to its cut; the public through the public reads, named by number; a caller with no seat gets what it gets today.
5. **Bounds** (D8): a member's message search reads the last 2,000 events through `recentEvents`; the public's the newest 200, what one public events read serves. `searched: { events, from_cursor }` says how far back a message search read.
6. **A search's ETag carries its query and the room's link**, so a stored poll's ETag never answers a search, nor a search's another.

## Consequences

- A match older than the bound is not found, and `searched` says so; past the bound a room gets an index in its object (D8), and semantic ranking is the named upgrade (D9).
- The 2,000 events a member's message search reads cross RPC from the room's object; at 20,000 characters each that can pass the RPC message limit. Matching inside the object is the upgrade, and it is where an index would go.
- A message's text is `payload.text`; a message sent with another shape is not found.
- `bellman_surface` keeps its MCP Apps `_meta`; a search answer has no `surface` key, so the App draws no canvas for it.
- A rollback is a revert: a client that never sends `query` sees nothing change.
````
