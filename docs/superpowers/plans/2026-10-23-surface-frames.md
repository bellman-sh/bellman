# Surface Frames Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This plan runs task by task with **one whole-branch review per PR, at the end**: no per-task review steps, whatever a skill says.

**Goal:** A surface holds 1,000 items, laid out by numbered frames: frame 1 is where every reader starts, and every surface read (the tool, `bellman_sync`, `bellman_confirm`, the member and public HTTP reads) answers one window of at most 64 items with the room's frames and a continuation. The dash's canvas opens on frame 1, steps the path and loads by viewport; the public Page view sorts Featured or Newest and pages.

**Architecture:**
- **Part 1, the server.** `src/surface.ts` learns the `frame` kind, `frame: N` and `locked`, and the 1,000 cap. A new runtime-free module, `src/frames.ts`, ranks frames, decides membership, pages a window, and places a write among frames (`placeSurfaceWrite`). A new store operation, `appendSurface`, runs that placement inside the write's transaction in both stores, so an overlap is refused there and a locked move writes every row it carries at consecutive cursors. `src/rooms.ts` reads windows once for the tool, the sync, the confirm and the HTTP reads.
- **Part 2, the dash.** The canvas reads the `region` window around its viewport, draws frames behind cards, steps the path and writes frames. The Page view gets `?sort=featured|newest` and pages. The Worker's feed, Markdown, item page and sitemap read `newest` or `key:` windows.

**Tech Stack:** TypeScript. bellman: Cloudflare Workers and SQLite-backed Durable Objects, zod, vitest 5 (root program) and `worker-tests/` (workerd). The dash: Vite 8, React 19, TanStack Router, React Flow, vitest 5.

**Spec:** `docs/superpowers/specs/2026-10-23-surface-frames-design.md` (approved 2026-10-23; bellman-sh/bellman#318, folds in bellman-sh/dash#71). It builds on `2026-10-22-surface-placement-design.md` (ADR 0030), `2026-10-18-room-pages-design.md`, `2026-10-22-topic-rooms-design.md` and `2026-10-23-room-search-design.md` (ADR 0034).

## Global Constraints

- **Reviews.** No per-task review; one whole-branch review per PR. The executor runs the plan task by task.
- **Writing.** A room holds many members: never a phrase that counts the room as a pair of sessions or names one peer as the only other one; say members, the room, or peers. Never a phrase the word scan of Task 8, Step 5 searches for (its pattern is the list), in code, comments, docs, commit messages or either PR. No em or en dashes in prose.
- **The numbers (D1, D2, D5).** `MAX_SURFACE_ITEMS = 1_000`; `MAX_FRAMES = 100`; a page is `SURFACE_PAGE = 64` items; a default card is `GRID`'s 320 by 200 wherever a placement omits `w` or `h`, on both sides.
- **The store is truth.** A window is computed from the rows on every read; no frame number and no frame index is stored. A frame's number is its rank by `createdAtOf`, ties by key.
- **Store methods** are async, every one; a new or changed method goes into `MemoryStore`, the Durable Objects store (`SessionDO` and the `DurableObjectStore` facade) and `tests/helpers/store-contract.ts`, which `tests/store.test.ts` and `worker-tests/store-contract.test.ts` both run.
- **Peer content is untrusted.** A frame's title is peer text: on a read it travels in `frames[]` beside the envelopes and the tool's text keeps `UNTRUSTED_PREAMBLE`; the dash renders it as React text; the join preview carries no title (R19).
- **No tool is added.** `extension/manifest.json` stays as it is and `tests/extension.test.ts` keeps passing. Tool text changes (R20) mean `npm run docs:gen` and a new measurement in ARCHITECTURE section 11.
- **Generated files.** `src/ui/assets.ts` is generated by `npm run build:ui`; `ui/` does not change here (the MCP App reads `surface.items` and gets the front window). `plugin/bridge/*.mjs` and `mod/hooks/register.mjs` are rebuilt only by release PRs, and neither PR here is one. The docs site's tool pages are written by `npm run docs:gen` and pinned by `tests/docs-reference.test.ts`.
- **Non-ASCII in TypeScript** is a braced escape: U+00B7 is `\u{B7}`. JSX text reads no escape, so there it goes in a string expression.
- **Tools.** Edit files with the Edit or Write tool, never `perl -i` or `sed -i`. Never call a `graph_*`, dual-graph or `bellman_*` tool. Never bypass commit signing: a commit that hangs or says "incorrect passphrase supplied" is a stop, reported to the lead.
- **Repos.** bellman is jj (`jj commit`); the dash is git, on a branch from `origin/main`. Every commit is signed. Nothing reaches `main` but through a PR.
- **Order.** Part 1 starts from trunk (room search's server part is in it). Part 2 starts after Part 1 deploys, and after room search's dash PR has merged (both edit `publicRoomRoute.validateSearch` and `PublicRoom`); if that PR is still unmerged then, the lead rules on the order.

## Review Focus

The inputs most likely to bite a person using this, each pinned in the task named.

1. **A card whose centre lies on the edge two touching frames share.** Expected: it belongs to exactly one of them (the right or lower one), counted once, read once. Task 2.
2. **A reader paging frame 2 while frame 1 is removed.** Expected: its `next` keeps reading the same frame, now answered as `frame:1`; a `next` for a frame since removed is refused with `NEXT_FRAME_GONE`, never answered from another frame. Task 2.
3. **A garbage or tampered `next` or `window` on the public read, which anyone can call.** Expected: 400 with the refusal text, never a 500 and never another window's items. Task 7.
4. **Two frame writes landing together that would overlap.** Expected: one lands, the other is refused naming the first, and the log holds one event. Task 4.
5. **A room with no frames and 64 items or fewer, read with no argument.** Expected: every item it answers today, connectors included, `frames: []`, `window: "newest"`, `next: null`, and the plain ETag `"<cursor>"`, so a client that reads `surface.items` sees no change. Task 6 and Task 7.

## Rulings

Where the spec leaves a choice, is silent, or meets the code, and what this plan does. **★** marks a ruling beyond the spec's letter.

- **R1. ★ The module.** `src/frames.ts`, runtime-free beside `src/surface.ts` and importing only from it and `src/types.ts`, is the one place a frame is ranked, a membership decided, a window paged, or a write placed among frames. Both stores import `placeSurfaceWrite` from it; `src/rooms.ts` imports `readWindow`. `surface.ts` does not import it, so there is no cycle. `coveredBoxes` is exported from `surface.ts` for it.
- **R2. The cap (D1).** `MAX_SURFACE_ITEMS = 1_000`, read where it is read today (`resolveSurfaceWrite`, before the append), still a courtesy bound. ★ The refusal writes the number out, as the link bound's "2,048" is: `this room's surface already holds 1,000 items; remove one with { key, remove: true } before adding "<key>".` `MAX_SLOT_SEARCH` stays derived (`MAX_SURFACE_ITEMS * GRID.cols`, 4,000) with no bound of its own (the builder's call): the worst case is 4,000 slots against 1,000 boxes, 4 million comparisons inside one transaction. Task 3 times it once and its `ponytail:` comment records the figure.
- **R3. The frame item (D2).** `frame` joins `SURFACE_KINDS` and `SurfaceKind`. A frame needs a title and a placement with `x`, `y`, `w` and `h`; it has no body, blob, ends or shape. ★ `locked` is `SurfaceItem.locked?: boolean`, set by `normalizeSurfaceWrite` on a frame alone (`v.locked ?? true`) and absent on every other row, so no existing fixture changes; the wire always carries `locked: boolean | null`. Refusals, verbatim, each behind the existing `surface <kind> "<key>": ` prefix: `a frame needs a title: its name on the canvas and the page`; `a frame needs placement { x, y, w, h }`; `a frame has no body`; `only a frame is locked`. The strict-shape refusal lists the fields as `{ key, kind, title?, body?, ends?, placement?, frame?, blob?, shape?, locked? }`.
- **R4. `frame: N` on a write (D2).** `SurfaceItemShape` gains `frame: z.number().int().positive().nullish()`. It is for `PLACED_KINDS` only, never beside a placement, never on a frame; it travels on `SurfaceWrite.frame?: number` and is never stored. Refusals, checked in this order after the kind's own rules: `a frame is not placed in a frame: frames do not nest`; `frame: <n> places text, link, diagram, file, image and html items`; `send placement or frame, not both`. ★ A key whose stored placement already has its centre in frame N keeps it, so a rewrite moves nothing; otherwise the write takes the lowest free `frameSlot` (R5). A missing frame and a full one refuse inside the transaction (R7).
- **R5. ★ The slots inside a frame.** `frameSlot(frame, i)`: columns `floor((w - GRID.gap) / (GRID.w + GRID.gap))`, rows `floor((h - GRID.gap) / (GRID.h + GRID.gap))`, slot `i` (left to right, then down, `i < cols * rows`) at `(x + GRID.gap + (i % cols) * (GRID.w + GRID.gap), y + GRID.gap + floor(i / cols) * (GRID.h + GRID.gap))`, else null. A slot is free when no box of `coveredBoxes(rows without frames, key)` overlaps it. A frame 1,480 by 520 holds four by two.
- **R6. Membership and the path (D2, D3, D4).** A row's box is its placement with `w` and `h` defaulting to `GRID`'s. ★ Its centre is in a frame when `fx <= cx < fx + fw` and `fy <= cy < fy + fh`, half-open, so a centre on an edge two touching frames share is in the right or lower frame only (Review Focus 1). Connectors, frames and rows with `placement: null` are in no frame. Frames rank by `createdAtOf` ascending, ties by key in code units; items in a frame order by top edge, left edge, key. ★ A key whose kind changes to or from `frame` is stamped `createdAt` afresh in `applySurfaceWrite`, as a removed key written again is, so a frame is always the next number and never jumps into the path by an old card's date.
- **R7. Placement among frames, in the transaction (D2).** `placeSurfaceWrite(rows, write)` (Task 3's Interfaces) answers the write to store, the writes a locked move carries, or a refusal. Overlap is a frame's box against every other frame's (its own key excluded), by `overlaps`, so touching edges pass. Refusals, verbatim: `surface frame "<key>" would overlap frame <n> ("<other>"): frames may touch but not overlap`; `surface <kind> "<key>": frame <n> does not exist: this room has <no frames | 1 frame | k frames>`; `surface <kind> "<key>": frame <n> ("<frame key>") has no free slot for a 320 by 200 card: place it with placement { x, y }, or make the frame larger`. A write with neither `frame` nor placement keeps `withPlacement`, whose `coveredBoxes` already counts every frame as covered, since a frame is a placed row.
- **R8. The locked move (D2; the event shape is the builder's call).** ★ The written `locked` decides, not the stored one: `{ ...frame, placement: moved, locked: false }` moves the frame alone, and a write that leaves `locked` out is locked (D2's default). When the stored row is a frame and the write's corner differs, the rows whose centre was in the old rectangle move by the corner's change (`dx`, `dy`); a write that keeps the corner (a resize) carries nothing. Each carried write is the row's item with its placement moved, in key order. ★ The log gets the frame's `surface` event, then one `surface` event per carried row at the cursors after it, each authored by the writer, `refId: null`, its payload the full normalised item as the row stores it, so every reader of a `surface` event and `restore` read it as any other version. ★ Like the dash's group drag today, a carried row takes the writer as its author and drops its approver (R20 of topic rooms); flagged to the lead.
- **R9. ★ The store operation.** `appendSurface(sessionId, e, extras, key)` (Task 4's Interfaces) is the path of every surface write: `writeSurface` calls it keyed or unkeyed (`null`, as `approveProposal`'s key is). It runs `placeSurfaceWrite` over the rows it lists in the transaction and answers `refused` with the reason, writing nothing. `approveProposal` runs the same step for the card it applies, so a proposed frame (D8) is held to the rule: `ApprovalWrite` gains `{ outcome: "refused"; reason: string }` and `carried: SessionEvent[]` on `appended`. `appendEvent` and `appendEventOnce` keep `extras.surface` for every other write and throw `FRAME_WRITE_PATH` for a frame-shaped one (`isFrameWrite`), so no path places a frame unchecked.
- **R10. The transaction's size (Risks).** `putRows` already puts at most `KEYS_PER_CALL` (128) keys a call through the one transaction. Task 4's workerd test moves a locked frame holding 900 cards and asserts all 901 events and rows land; a failure there is a stop reported to the lead, not a cap invented in the task.
- **R11. At most 100 frames (D2).** Read in `resolveSurfaceWrite` beside the item cap, a courtesy bound: `this room's surface already holds 100 frames; remove one with { key, remove: true } before adding frame "<key>".` A rewrite of an existing frame key passes.
- **R12. ★ The window parameter.** One string, `window`, on `bellman_surface` and as `?window=` on both HTTP surface reads, with `next` beside it (`?next=`). The grammar: `newest`, `unframed`, `frame:<n>` (`n` a whole number from 1, no leading zero); HTTP also takes `region:<x>,<y>,<w>,<h>` (finite numbers, `w` and `h` above 0) and ★ `key:<key>` (the surface key grammar), the one item with that key, for the dash's item page and its taken-key check. `region` is HTTP only (the builder's call: the spec's table gives it to the canvas alone). Refusals: `WINDOW_REFUSAL_TOOL`, `WINDOW_REFUSAL_HTTP`, `NEXT_ALONE`, `NEXT_REFUSAL`, `NEXT_FRAME_GONE`, `noSuchFrame(n, count)` (Task 2's Interfaces), and `QUERY_WITH_WINDOW` for `query` beside either.
- **R13. What a window holds (D5).** `frame:<n>`: the rows in frame n, canvas order. `unframed`: the rows in no frame, newest first (`createdAtOf` descending, key ascending). `newest`: every row, newest first. `region`: the rows whose centre is in the rectangle, a row with no placement at the grid slot viewers draw it in (by key order among the rows with none, `toFlow`'s rule), canvas order. `key:<key>`: that row, frame or not, or none. In every window but `key:`, frames and connectors are not ranked items. ★ The frames a region intersects are carried by `frames[]`, which lists every frame with its placement on every answer, so no frame row repeats in `items`. ★ Each page carries after its items every connector with an end among them; connectors do not count toward the 64. That is how the spec's two sentences on connectors meet: `newest` ranks none, and a frameless room's front read still answers its connectors (Review Focus 5).
- **R14. ★ The page and its token (the builder's call).** `SURFACE_PAGE = 64`. `next` is `null` when the window holds no more, else a keyset position: base64url of a JSON array, `["newest", createdAt, key]`, `["unframed", createdAt, key]`, `["frame", <frame key>, y, x, key]` or `["region", x, y, w, h, posY, posX, key]`. A frame's token carries the frame's key, not its number, so a removal ahead of it does not move the reader to another frame (Review Focus 2). A token that does not decode to one of those shapes is `NEXT_REFUSAL`. `next` is always present.
- **R15. The answer's shape (D5).** The tool, the sync and the confirm answer `surface: { cursor, items, frames, window, next }`; the HTTP reads `{ surface_cursor, items, frames, window, next }`, and ★ a region answer adds `slots: { [key]: { x, y } }`, the grid slot of each row on the page that has no placement, since the dash holds only the region and cannot count the others. A `frames[]` entry is `{ number, key, title, placement: { x, y, w, h }, locked, count }`; ★ `locked` is beyond the spec's list, for the canvas's lock control and the Page view.
- **R16. The front, and the validators (D5).** No window is the front: `frame:1` when the reader sees a frame, else `newest`; `window` names which. ★ The no-argument HTTP read keeps `surfaceTag` (`"<cursor>"`), so today's polls keep their 304s. A windowed read's ETag is `windowTag(cursor, asked, next)`: the canonical name of the window asked (`""` when only `next` was sent) and the `next` asked (`""` when none), built from the request, so the 304 path needs no row. It has three colons where `searchTag` has two, so no tag of one kind equals one of the other.
- **R17. The cut (D5).** `surfaceAt` filters the rows first; every rank, membership, count and page is then computed over what the member may see.
- **R18. Search (D5).** `CardResult.data` gains `frame: number | null`, from `frameNumbers(rows)` over the same rows; ★ a frame's own hit carries its own number. The search's bound becomes `MAX_SURFACE_ITEMS`. `query` beside `window` or `next` is refused with `QUERY_WITH_WINDOW`.
- **R19. ★ The join preview (D5).** `bellman_connect`'s `surface` is `{ cursor, items, frames }`: `items` is `surfaceIndex` over the front window's rows, and `frames` is `[{ number, key, count }]`, with no title, because the preview carries no prose (`surfaceIndex`'s rule, pinned in `tests/working-surface.test.ts`).
- **R20. ★ The tool texts.** `bellman_surface`, `bellman_sync`, `bellman_confirm` and `bellman_connect` (the spec's four), and `bellman_send`, whose `surface` line names the payload's fields and "at most 64 per room" (predicate P3). Task 8 gives the words.
- **R21. Refusal statuses.** The tool answers each refusal as an error. HTTP reads answer a window refusal 400 `invalid_request`. Writes keep `writeSurface`'s kinds: overlap and a full frame are `conflict` (409), a missing frame and the shape rules `invalid` (400), the frame cap `conflict`.
- **R22. ★ The RPC cost.** Windows are computed in the Worker from `surfaceOf`, as search is. At 1,000 rows of up to 8,000 characters a read carries several megabytes across RPC, where 64 rows carried a few hundred kilobytes; `readWindow` carries a `ponytail:` comment naming that ceiling and the upgrade, a store method that pages inside the room's object. Flagged to the lead.
- **R23. ★ Tests that fill the surface** seed rows through the store with explicit placements, not 1,000 tool calls or 1,000 slot searches; only the write under test goes through the path it tests.
- **R24. The ADR is numbered at the PR:** `docs/adr/00NN-surface-frames.md`. When this plan was written, `origin/main` held up to 0036, local branches held 0033 (a2a) and 0037 (agent auth), and no PR was open, so it would be 0038. Number against `origin/main`, every open PR and every local branch when the PR opens.

Part 2's rulings:

- **R25. ★ The canvas's region (D7; margin and pages are the builder's call).** The region is the viewport in flow coordinates grown by one viewport on each side (three viewports wide and high), rounded out to whole pixels; it is read again on `onMoveEnd` when the viewport leaves the middle third of the last region. A region read takes pages until `next` is null or `MAX_REGION_PAGES = 4` (256 items) are held, which is also the Risks' cap on what the canvas draws of one large frame. Only the latest region is kept. The poll reads page 1 with its ETag and every page again when it changed.
- **R26. ★ How the canvas opens.** The first read is the front (no window). A link's `?item=` reads `key:<key>` and fits to its placement (or its slot); else, with frames, it fits to frame 1's placement; else it fits to the front's items as today. Reads go to the region from the first `onMoveEnd`.
- **R27. ★ Frames on the canvas.** A React Flow node of type `frame` per `frames[]` entry, `zIndex` `FRAME_Z = -1_000` (behind every shape, whose `shapeZ` is at most -1 and above -200), its tab reading `<number> \u{B7} <title>` as React text, a lock control for a writer. Previous and Next buttons step the path and fit each frame (`flow.fitBounds`), with `Frame <n> of <k>` between them.
- **R28. ★ Writing frames.** A Frame button after Shape opens `FrameDialog` (title, Locked checked by default); the frame goes where the person is looking at `FRAME_DEFAULT = { w: 1_480, h: 520 }`, four by two cards by R5. A refusal (an overlap, the 100 cap) shows in the dialog. Dragging or resizing a frame writes it (`frameWrite`); the members of a locked frame follow on the read after the write lands, with no local carry.
- **R29. ★ One item by key.** The taken-key check in `TextDialog`, the item route's loader and the Worker's item head read `key:<key>`, never a window they search.
- **R30. ★ The Page view (D6).** `?sort=featured|newest` on `/r/$roomId`; with none, Featured when the front read answers `window: "frame:1"`, else Newest. Featured: per frame a heading `<n>. <title>` and its items rendered as the page renders items today (an `Article` per item but connectors, in canvas order), then a heading `More` over `unframed`; it starts with frame 1's first page and ends with a button `Next: <n>. <title>` (or `More from this frame` while the frame's `next` holds, or `More` for the unframed items). Newest is today's order with `Older` at the end. Only the first page polls; a page loaded by a button is read once.
- **R31. ★ The Worker.** The feed and the Markdown read `?window=newest` once and take its first `FEED_ITEMS = 50` text items; a room whose newest 64 hold fewer text items carries fewer. The item head reads `key:`. The sitemap lists each room's newest 64; flagged to the lead (a blog past 64 posts loses the older ones from the sitemap until it pages).
- **R32. ★ The side panel** lists the frames (number and title, each locating its frame) and then the items in view.

## Lead rulings (2026-10-23)

These override the planner's rulings where they differ. Each records what was decided, why, and what it costs if wrong.

- **L1, over R22: windows are computed inside the room's object, not in the Worker.** A new `BellmanStore` method, `surfaceWindow(sessionId: string, window: SurfaceWindow, opts: { cut?: number; next?: string }): Promise<WindowRead>`, in `MemoryStore`, `SessionDO` (through `DurableObjectStore`) and `tests/helpers/store-contract.ts`, returns one page of a window plus `frames[]`, so a read crosses RPC with at most 64 items. `src/frames.ts` stays runtime-free and holds the ranking, membership and paging both stores call. `surfaceOf` keeps the callers that need every row (the sweep, search). Why: 1,000 rows of up to 8,000 characters is megabytes across RPC on every read and every poll. Cost if wrong: a store method to remove later.
- **L2, over R8: a carried card keeps its author and its approver.** A locked move changes a carried row's placement and nothing else: `byMemberId`, `byLabel`, `createdAt` and `approvedBy` stay. The log still gets one `surface` event per carried row, at consecutive cursors after the frame's, authored by the mover with the full item, so `restore` reads every version as today; the event's author is who moved it, the row's author is who wrote it. Why: moving a frame is not authoring its cards, and the topic room page and the blog credit the writer and the approver. Cost if wrong: one rule in `appendSurface`. The ADR records that a large locked move writes one event per card into every member's `bellman_sync`.
- **L3, on R31: stands.** The sitemap lists each room's newest 64 until the sitemap pages; the ADR names the limit.
- **L4: the item page and the Worker read one item through the `key:<key>` window (R12)**, never through `newest`, so an item older than the newest 64 still has its page.
- **L5: R6 stands.** A kind change to or from `frame` sets `createdAt` afresh, so a converted card joins the path at its end, as D3 says.

export interface FrameEntry { number: number; key: string; title: string; placement: { x: number; y: number; w: number; h: number }; locked: boolean; count: number }

export const WINDOW_REFUSAL_TOOL = "window must be newest, unframed or frame:<n>, n a whole number from 1";

export const NEXT_REFUSAL = "next is not a continuation this server wrote: read the window again without it";
export const NEXT_FRAME_GONE = "the frame next was reading is no longer on the surface: read frames[] and choose again";

export const noSuchFrame: (n: number, count: number) => string; // "frame 3 does not exist: this room has 2 frames" ("no frames", "1 frame")

export function parseWindow(raw: string, offered: "tool" | "http"): { ok: true; window: Window } | { ok: false; reason: string };
export function windowName(w: Window): string;                       // "frame:2", "newest", "region:0,0,800,600", "key:intro"
export function rankFrames(rows: readonly SurfaceRow[]): SurfaceRow[]; // the frames, path order (R6)
export function frameEntries(rows: readonly SurfaceRow[]): FrameEntry[];
export function frameNumbers(rows: readonly SurfaceRow[]): Map<string, number | null>; // every key; a frame its own number (R18)

export interface WindowPage { window: string; items: SurfaceRow[]; next: string | null; frames: FrameEntry[]; slots?: Record<string, { x: number; y: number }> }

````markdown
# ADR 00NN: Surface frames, and a surface of 1,000 items

**Date:** 2026-10-23 · **Status:** accepted · **Spec:** `docs/superpowers/specs/2026-10-23-surface-frames-design.md` · **Plan:** `docs/superpowers/plans/2026-10-23-surface-frames.md`

## Context

A surface held 64 items so one read fit one tool response. Topic rooms and the blog accumulate cards for months; 64 was too few, and 1,000 read at once is too much for an agent, a poll or a page.

## Decision

1. **A surface holds 1,000 items** (D1), a courtesy bound read before the append, as ADR 0015 made the 64.
2. **A frame is a surface kind** (D2): a titled rectangle, locked unless written otherwise. A card belongs to the frame holding its centre; frames never overlap, refused inside the write's transaction by `appendSurface`, the store operation every surface write goes through; at most 100.
3. **The path is creation order** (D3): a frame's number is its rank by `createdAt`, computed on every read and never stored.
4. **Every read is a window** (D5): `frame:<n>`, `unframed`, `newest`, and over HTTP `region` and `key`, at most 64 items, with `frames[]` and a keyset `next`. No argument reads the room's front: frame 1, or newest.
5. **A locked move is one write that changes many rows** (D2): one `surface` event per row, at consecutive cursors, in one transaction.

## Consequences

- A client that reads only `surface.items` sees the front window. In a room with no frames and 64 items or fewer that is every item, as before.
- A locked frame's move rewrites its cards' rows under the mover's name, as a drag of the same cards does, and adds one event per card to every member's log.
- Windows are computed in the Worker from every row, so a read of a full surface carries every row across RPC; paging inside the room's object is the upgrade.
- A rollback is a revert while no room holds a frame or more than 64 items; after that, the rows are readable by the old code but a frame reads as an unknown kind.
````
